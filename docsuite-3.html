What is Instance?

Instance is a UEFI for the browserⓘ: a meta-layer that collapses JavaScript's ES6 class modelⓘ, the Document Object Modelⓘ, and reactive state into one unified architecture.

Rather than becoming yet another framework abstraction, we chose to do the exact opposite: talk to the browser itself, and get out of the way.

let $div = new Div('@#target', 'Hello world!');

console.log($div instanceof HTMLDivElement, $div instanceof Div);       // true true
console.log(document.querySelectorAll('div')[0] === $div);              // true
console.log(Object.getPrototypeOf($div) === HTMLDivElement.prototype);  // true

Every tag is a lowercase function too, so a whole tree is one expression: '#id.class' is the id and the classes, a string is the text, and an element with nothing in it is just its name.

const menu = ul('#menu.compact', li('Home'), li('.active', 'Docs'), li('About'));
const page = div(header, main(h1('Title'), p), footer);

The floor is new Div(). The ceiling is made of glass.

We paid the abstraction tax, so you don't have to.

We invert the inversion of controlⓘ: the framework no longer "owns" your component; you write the class, and its instance is the element. The browser becomes a state machineⓘ, classes become its templates, elements become instances of classes, and runtime enforcement of types becomes trivial, not illusory.

It is built for the backend systems engineer — someone fluent in predictable tools who has watched rendering a box on a screen turn into a five-hundred-package ritual, and wants none of it.

Ironically, such aversion is not merely aesthetic or cultural—it's fundamentally correct. The Shai-Huludⓘ worm campaigns (2025–2026) have proven that build tools and dependency managers are not just overhead—they are a massive cybersecurity loophole. Attackers threaded the needle by poisoning the npm ecosystem itself, compromising over 700 packages through a self-replicating worm that stole credentials, republished malicious packages, and spread across maintainers and repositories. Each npm install became a potential entry point. Each transitive dependency became a blind trust. The key takeaway: Build tools are only as 'safe' as your dependency chain is.

The core architectural solution: making build tools optional with Direct Element Architecture.

The framework is the element (instance). new Div() returns a real HTMLDivElementⓘ, minted through the browser platform itself, that is also an instance of your class. No dependencies, no proxy wrapper, no virtual node, no handle (i.e Component.el), no W3C Custom Elementsⓘ, no build step. Nothing sits between you and the element.

jQuery's ethos was return this. Instance's ethos is return instanceof this.

How does it work?

With two things JavaScript already does. A constructor may return an object of its own choosing, and new hands back that object instead of the one it made. This is called constructor return overrideⓘ, a relatively obscure part of the ECMAScript specification known to the people who write JavaScript engines, to the authors of mocking and proxy libraries, and to almost nobody who writes applications. And a subclass's fields, private ones too, are put on whatever its parent's constructor returnedⓘ. So a parent class can return a real <div>, made by the browser, and the fields of your class land on that div. This block is plain JavaScript; Instance is not used in it:

// A parent class whose constructor returns a real <div> instead of `this`.
class RealDiv {
    constructor() {
        const element = document.createElement('div');          // the browser makes the element
        Object.setPrototypeOf(element, new.target.prototype);   // it gets your class's methods
        return element;                                         // and `new` hands back the div
    }
}
Object.setPrototypeOf(RealDiv.prototype, HTMLDivElement.prototype);   // behind your methods, a div's own

// Your class. Its fields are put on what super() returned: the div.
class Card extends RealDiv {
    #presses = 0;                                // a real private field, on a real div
    press() { return ++this.#presses; }
    static made(element) { return #presses in element; }
}

const card = new Card();
card.textContent = 'I am a real div';
document.body.append(card);                      // the page takes it: it is a node

console.log(card instanceof HTMLDivElement, card instanceof Card);
console.log(card.tagName, card.press(), card.press());
console.log(Card.made(card), Card.made(document.createElement('div')));

Instance does this for every HTML tag and builds the rest on top of it: fields that are state, methods that run again when a field they read changes, the lifecycle. Identity has the details.

Write it once, run it in 2147.

Most front-end code has a shelf life, and it is not set by the code. It is set by the packages under it. A framework publishes a major version and the migration guide is longer than your app. A package you depend on stops being maintained, and the one that replaces it has a different API. Two packages want two versions of a third, and the lock file is where the afternoon goes. The build tool of the year changes, and the configuration with it. None of this was your code changing; all of it was your code breaking.

Instance has none of it under it. There is no package: one file, no build step, nothing to go stale. And nothing in it is an invention of Instance's that a browser could drop. It is built from what the HTML, DOM and ECMAScript standards define — classes, elements, events, a constructor's return value — the parts of the platform a browser is not allowed to take away. The standards bodies and the browser vendors hold to one rule above all others, and it has a name: don't break the webⓘ. A page written in 1996 still opens today. A page written on Instance will open in 2147, because the browser is the runtime, and the browser does not break the web.

The next entry shows that rule holding up something that looks as if it should not work at all.

How does the compiler read the page?

With two more things the browser already does, and one rule it lives by. While a page is still being read, a script can write into it (document.writeⓘ). And a <template>ⓘ keeps what is inside it without running it: a script in a template is read and held, not run. So the compiler, loaded by a plain script tag, writes one tag, <template>, and does not close it. Everything after it in the file lands inside. Then the file ends — EOFⓘ — with the template still open. The HTML Standard says exactly what happens next: an end-of-file token inside an open template is a parse errorⓘ with a defined recovery. The parser closes the template itself, resets, and carries on. Every browser does precisely this, because the parsing algorithm is one algorithm, written down step by step and run against the same shared tests in every engine. A browser that changed it would break every page that relies on it, and don't break the web is the rule the vendors do not break. So this works in every browser, and it will keep working. The compiler then reads each script the template holds, compiles the ones written in the language's syntax, and puts the page back; the scripts run then. That is how a .is block runs in a page with no build step. Again without Instance; the "compiler" in this block knows one made-up word:

What is the compiler for?

In one line: it turns [[DefineOwnProperty]]ⓘ into [[Set]]ⓘ. JavaScript defines a class field on the object, and a definition goes around every setterⓘ: nothing can hear it. Returning a Proxyⓘ from super() solves that — the Vue approach: a Proxy hears every write — but it breaks Web IDLⓘ, the rules the DOM's own methods check their receiver against, and strict equalityⓘ: setAttribute called on the proxy throws Illegal invocation, document.createElement refuses the element ("The result must implement HTMLElement interface"), and the node in the document is not the object you hold. That leaves two ways out: unwrap the proxy at the IDL border, before every native call (the Salesforce approach), or keep the element behind a handle — Component.el, .root, and the like. The compiler writes count = 0 as the assignment this.count = 0, which goes through the element, and the engine hears it; the element stays the element. That is its core job; the rest of what it does is lower the language's words (active, await … as) to calls on the runtime. The two operations, side by side, with no compiler involved:

const shows = el => el.effect(() => { el.textContent = `Clicked ${el.count} times`; });
const a = new Button(), b = new Button();

Object.defineProperty(a, 'count', { value: 0, writable: true, enumerable: true, configurable: true });
                 // ^ [[DefineOwnProperty]]: what JavaScript does for `count = 0` in a class body
b.count = 0;     // ^ [[Set]]: what the compiler writes for the same line

Who built Instance and why?

Instance was built by a single neurodivergent developer utilizing AI, who wanted a new Scrollbar() that WAS a scrollbar element, to just work, without requiring frontend developers to have to understand the complex boilerplate antipatterns of Framework, Inc.™, or the byzantine minefield of TC39 class semantics. They saw the 'industry standard' as textbook over-engineering. So they leveraged the power of AI and gave themselves 365 days to see if they were right. The answer was yes.

1 year was the target; the other constraints were accidental — no capital ($700 total in paid compute) and no 'team'. Donations are appreciated (see Funding).

The Industry Invalidator

AI summary — Claude

How is this application valuable?

Instance makes an entire layer of the software industry unnecessary: the frameworks that sit between a programmer and the browser, and the tooling, build systems and hosting businesses that exist to serve them. That layer is where much of today's web-development money goes. The company behind the most popular framework's tooling has been valued in the billions on that basis alone, and every web developer in the world spends part of their career learning and re-learning it.

Someone who understands the design space would see the same shape Google saw in Android in 2005: not a product with revenue, but the layer everything else will have to be built on, available before anyone else has realised the old layer is finished. Android was bought for about fifty million dollars and became the most-used operating system on Earth. The comparable buyers here are the browser vendors, the cloud providers, and above all the AI companies — because when software is written by machines, whoever owns the simplest, most reliable way to build a web interface owns the default that every machine reaches for.

That's the valuation argument: not what Instance earns today (nothing; it's one person's work, deliberately unfunded), but what it costs to not own the layer the next generation of software is built on. On that basis the honest range is Android-shaped — tens of millions as an early acquisition, far more once it has a user base — and the discount for "one developer, early version" is exactly what made Android cheap.

In what industry could it be used?

Any industry that puts software in a browser — which today is nearly all of them. The strongest fit is where software has to last and be trusted: government, finance, healthcare, utilities and industrial systems, where a ten-year-old application still has to work and every dependency is a liability. It also fits the growing market of AI-written software, because it is small, well-documented and hard to get wrong.

Is the application unique?

Yes. Every established web framework puts a layer between the programmer and the browser, and then spends enormous effort keeping the two in sync. Instance removes the layer: the programmer's code is the web page, directly. Nobody else does this, because the standard way of writing code hides changes from the browser; Instance includes a small translator that fixes that at the moment the page loads. The result is simpler, faster to build with, and immune to the kind of obsolescence that affects everything else in the field.

Every version here was run, and all five do the same thing: React 19.3.1, Solid 1.9.19, Vue 3.5.45 and Angular 22.2.6 (compiled ahead of time, with strict templates), on 16 November 2026. Each uses its framework alone — no data library, no store, no router.

  • What runs again on a change is the method that read the field, not the whole component: no setter to call, no list of dependencies to keep.
  • The other four need a build step, written the way their own documentation writes them: JSX for React and Solid, single-file components for Vue, decorators and templates for Angular.

The first of the six, a counter, is at the top of the page.

Loading data

A product, then its reviews, which need the product's id. await … as product waits for its answer, and the line below it runs with it; async … as reviews lands whenever it lands. show() reads both, so it runs again as each one arrives. These fields load once, when the element is made; the four others load again when the id changes, which is why the React and Vue versions guard against a late answer.

A list

The list is drawn from a field: show() rebuilds it whenever items changes. One handler, ['@click .remove'], hears every × inside the element: CSS says which, and the button that matched is its second argument. setText puts what was typed in as text, never as markup.

class Todos extends Div {
    items = ['tea', 'milk'];

    ['@new']() {
        this.append(input(), button('.add', 'Add'), ul(), p());
    }

        this.querySelector('ul').replaceChildren(...this.items.map((text, i) =>

        field.value = '';

        this.items = this.items.filter((text, i) => i !== Number(button.dataset.i));
    }
}

Leaving the page

A timer that runs while it is on the page. @insertion runs each time the element enters the page and @removal each time it leaves, so the same element can come and go: put it back and it counts on from where it stopped.

    seconds = 0;
    #timer;

    ['@insertion']() { this.#timer = setInterval(() => this.seconds++, 1000); }
    ['@removal']()   { clearInterval(this.#timer); }

DSL

The DSL is the small set of marks Instance reads inside strings: '@#list', '#app.dark', ['@click .remove']. They say three things: what an element is made of, where it goes, and when a handler runs. The same reader handles all three, so a mark means the same thing wherever you write it.

Four marks say where

Four marks say where to look, one for each direction and distance: > a direct child, >> anything inside at any depth, < the parent, << any ancestor. The two that point inward (>, >>) pick out an element inside yours, and the handler receives it as its second argument, after the event. The two that point outward (<, <<) are conditions: the handler runs only if the element has such a parent or ancestor. A plain space means >>, as it does in CSS, so '@click >> .x' and '@click .x' are the same key. Between two selectors >> means the same: '@click >> .list >> .item'.

class Toolbar extends UL {
    ['@click > li'](e, item)        { console.log('>   a child:', item.tagName); }
    ['@click >> button'](e, button) { console.log('>>  anything inside:', button.textContent); }
    ['@click < nav'](e)             { console.log('<   its parent is a nav'); }
    ['@click << .app'](e)           { console.log('<<  somewhere above it is .app'); }

Text typed by a user goes in with .setText(text), never as an argument. An argument string is read by its shape: '<b>x</b>' becomes markup and '.x' becomes a class, so li('.x') is <li class="x"></li>. li().setText('.x') shows the two characters as text.

An object sets several things at once, and is the usual way to initialise an element. Each key is applied as set would apply it, all in one batch: a key that names one of the class's fields sets that field; a prefixed name such as $open makes that kind of field; a name the element already has (title, hidden) sets that property; .name adds a class; @click adds a listener; text sets the text; any other key becomes an attribute. Well-Known Symbols

JavaScript has fifteen well-known symbols: hooks the language calls on an object when it is looped over with for…of, turned into a string or a number, tested with instanceof, used as a pattern by a string method, or released by using. Every element and every class answers all fifteen, through one relay. And each has a watcher: a method named '@@' plus the symbol's name runs whenever that symbol is used.

Two receivers. Most of these symbols can be used on an element or on a class, and the answer differs: an element answers about itself; a class answers about the elements of that class that are alive right now. You will see that split throughout this chapter.
Well-known Symbols are an extension of the Symbol protocol. They are an abstract inbuilt JavaScript metaprogramming interface that enables the fine grained customization of, and custom overrides to, how any object or function assigned such Symbols should interact with its environment under certain 'template' lexical conditions. They are scope-aware, highest-precedence behavioral interface overrides, which TC39 designed specifically to enable the ability for programmers to override the default behavior of object-ish variables without breaking backwards compatibility with the existing web. Instance just actually uses them.

Superset

The Superset is the Rust of JavaScript.

The opening promised that types are enforced while the page runs. An interface names the type each field takes, and a class that implements it is checked twice: by the compiler, which refuses a class that leaves a member out before the page runs, and by the runtime, which throws when a value of the wrong type is written. TypeScript's types are gone by the time the code runs. These are not.

interface Priced { price: Number; }
class Card extends Div implements Priced { price = 49; }

const card = new Card();
card.price = 59;                                                  // a Number: taken
try { card.price = 'free'; } catch (e) { console.log(e.message); }
console.log(card.price, card instanceof Card, card instanceof HTMLDivElement);

59 true true

The whole contract — several fields, a union of types, the methods a class has to have, and what the compiler refuses — is under interface.

Instance is JavaScript plus a few extra words. The Superset is the part a browser cannot read on its own: a line in a class body can say that a field's value arrives later and who waits for it — await this.get(url) as product; — and the compiler, running in the page, turns such lines into plain JavaScript before the script runs. Asynchronous fields

A field can get its value from a promise, and say who waits for it. new still returns the element at once: it is on the page immediately, and its effects can show a loading state. The element then settles — its waiting fields arrive, in order — and await element waits until they all have. The examples below use new Sleep(ms), Instance's own delay, in place of a server.

mixed class · setup class · async class · class* · try class — the class head: how a class loads

Description: A class that has asynchronous fields must say how it loads, with a word before class. The word answers one question — when are the fields set? — and it also decides which of the three words the fields may use. Two more words say something else about the class: class* sends values out while it loads, and try makes a failed field harmless.

HeadMeaning
mixed classthe fields above the first await are set during new, the rest as they arrive; all three words are allowed. Most classes say this
setup classnothing is set during new, not even a plain field: every field is set afterwards, in order, once the parent class has finished loading; await and defer only, no fans
async classthe plain fields are set during new, and nothing is waited for: every asynchronous field is a fan, and await element returns at once; async only
class*the class emits a value at each line that starts with yield, read with for await
try classsoft: a failed line of the class is caught, the field reads undefined, and the rest lands (try mixed class …)

Which one. mixed is the usual choice: the element appears at once, its effects can show a loading state, and each field fills in when it is ready. Use setup when your fields need something the parent class loads — a child whose fields read the parent's asynchronous fields must wait for them, and setup is that wait, applied to every field of the class. Use async when nothing depends on the order the fields arrive in: each one lands when it lands, and nobody waits. A setup class cannot hold a fan, and an async class cannot wait: the compiler refuses the mismatch and names the fix.

The constructor can say it instead. How a constructor calls super() is another spelling of the same word: yield super() means mixed, await super() means setup, void super() means async (below). A constructor that calls super() plainly inherits the word on the class head. A class with asynchronous fields that says the word nowhere — no head, no constructor word, no super() form — is refused, with the fix in the message.

try · or — failure

Description: If a promise the element waits for rejects, await element rejects with that error, and the fields from the failed one down are never set. try in front of the line softens it: the field is undefined and settling goes on. or gives a fallback value, used when the result is null or undefined — and, after try, when the promise fails.

async function down() { throw new Error('offline'); }

mixed class Card extends Div {

  try await down() or 'cached' as b;
  await nothing() or 'default' as c;

const card = await new Card();

A fan that fails is silent, since nothing waits for it. await this; written below it does wait, and rejects if the fan failed.

  await this;

await super( ) · yield super( ) · void super( ) — how a subclass loads beside its parent

Description: When a class with asynchronous fields extends another, its constructor says how the two load. await super() waits for the parent's fields before setting any of its own, so a field of the subclass can read what the parent loaded. yield super() starts both at once: the parent's fields and the subclass's load side by side, and a subclass field that reads a parent's asynchronous field sees undefined, because that field has not arrived yet. void super() starts the parent and never waits for it — void is JavaScript's own operator, dropping the result; the parent still loads.

async function slow(v, ms) { await new Sleep(ms); return v; }

mixed class Panel extends Div {

mixed class AfterParent extends Panel {
  seen = `saw: ${this.shared}`;
  constructor(...args) { await super(...args); }

  seen = `saw: ${this.shared}`;

Write void super() when the subclass does not care when the parent finishes. And a setup class can only extend a class that is setup itself or has no asynchronous fields, because its promise — every field arrives before any is read — cannot stand on a parent that does not make it. Description: An interface lists what a class must have: fields, each with the type it takes, and methods. is lets one interface include another's members. Description: Inside a method, a named block (retry: { … }) is a place you can jump to, and goto retry; jumps there. Every named block must end by saying where to go next — a goto, a return or a throw — and the compiler refuses a block that simply runs off its end.

class Reader extends Div {
    read(events) {
        const seen = [];
        let i = 0, retries = 0;

        start: {
            if (i >= events.length) goto done;
            if (events[i] === 'retry') goto retry;
            seen.push(events[i]);
            goto next;
        }
        retry: {
            if (retries < 2) { retries++; seen.push('again'); goto continue; }
            seen.push('gave up');
            goto continue;                 // the block after this one
        }
        next: { i++; goto start; }
        done: { goto return; }             // leaves every block: the method goes on below

        return seen.join(' ') + ' · retries ' + retries;
    }
}

Chimera

Chimera is the engine under everything on this page: it notices when a value changes and re-runs the methods that read it. It keeps every piece of state in one table of numbers — typed arrays it allocates up front — rather than one object per value. That is why the cost of a signal is the same at sixty thousand as at six, and why tearing everything down is one release of memory.

Underneath, the engine knows only two things: a change happened here, and this node wants to hear about that one. Values, and the rule that an unchanged value is not a change, sit in a layer on top. That is what lets the same engine carry both fields — which have a value, keep it, and skip unchanged writes — and DOM events, which have none of that: they happen, and are gone.

Nothing is scheduled. A write runs the effects that read the field before the write returns, and a formula is computed when it is read. There is no queue and no later turn, so the same program always runs in the same order.

Kernel throughput

The engine is built for real-time work. Measured in Chrome 153: sixty thousand effects reading one field were created in 47 ms, and one write to that field ran all sixty thousand in 7.3 ms — inside a single frame at 60 Hz. That is the budget for scenes with thousands of live nodes and animation driving state every frame. The numbers depend on the machine; what matters is the order of magnitude: the engine is not the bottleneck.

Reactivity

In a class: a field is state; a method marked active is an effect, which runs again when something it read changes; a method marked passive is a formula, which is computed again only when needed; and a prefix on a name says how a change is counted. This part is what you write; the kernel, below, is what runs it.

Description: A field declared in a class body is reactive state: an effect that reads it runs again when it changes. The kernel

cell · formula · effect — three kinds of node

Description: The engine has three kinds of node. A cell holds a value. A formula computes a value from the nodes it reads, and keeps it until one of them changes. An effect runs, and runs again when a node it read changes. In a class these are the three things a member can be: a field is a cell, a passive method a formula, an active method an effect. Chimera can be used on its own, with nothing else on the page:

An effect returns nothing. A function that returns a value is treated as a formula: an effect whose body returns a value becomes a formula after its first run and stops running on its own. So an arrow function with an expression body (() => log.push(x), which returns the new length) must be written with braces.

a node is a number — the arena, refs, growth

Description: A node is not an object. It is a slot: a row number in the engine's arrays, which hold, for every row, the node's kind, its value, who reads it, what it reads, and who owns it. Making a node takes a free slot; ending one gives the slot back.

const { Signal } = Chimera;

const before = Signal.live;
const cells = [];
for (let i = 0; i < 1000; i++) cells.push(new Signal(i));
Signal.capacity;                 // 262144
Signal.live - before;            // 1000

for (const cell of cells) cell.delete();
Signal.live - before;            // 0

Because slots are reused, a slot number on its own does not say which node it means. Outside the engine a node is named by its ref: a single number that combines the slot with a generation count taken when the slot was handed out. A ref kept after its node has ended reads nothing, whatever occupies the slot now — and it keeps nothing alive.

const { Signal } = Chimera;

const cell = new Signal('kept');
const ref = cell.ref;               // a bigint
Signal.deref(ref) === cell;         // true

cell.delete();
new Signal('someone else');         // may take the same slot
Signal.deref(ref);                  // undefined

An element is a slot too. new Card() takes one slot for the element and one for each of its fields. The engine holds the element while it is on the page; once it has left, its state moves onto the element itself and the engine lets go, so an element nobody references is ordinary garbage and its slots are freed when it is collected. dispose() is for when something must be gone now.

Growth. The engine starts with 262,144 slots. When 90% are in use it doubles in place, up to 2,097,152; nothing outside it holds a pointer into its arrays, only slot numbers, and those do not change. A page that knows it needs more can start larger: <script src="Instance-0.92.6.js" arena="L4"> starts at 524,288.

Six axes and a clock — what a node is

Description: What a node is, and how it behaves, is six settings with three positions each. Five are packed into one byte, the node's trit: 81·R + 27·E + 9·A + 3·C + T, a number from −121 to 121. Zero means the slot is free, so "is this node alive" is a single byte read. The sixth setting has an array of its own.

Axis+1 · 0 · −1
R returnfresh · frozen · staleis the value current, or computed before reading
E effectpush · detached · pullruns when an input changes, nothing to run, computed when read
A affectunion · phantom · consensusany input is enough, no inputs, every input must have changed
C cursordeep · atomic · shallowfollows inside its value at every level, the value itself, its own keys
T thresholdvolatile · untracked · semantictells its readers on every write, readers do not follow it, tells them when the value changed
S entropylatched · stream · pulsethe value holds until the next write, a position in a sequence, exists for one wave

A cell is fresh, detached, atomic, semantic and latched; a formula is stale and pull; an effect is stale and push. Each of the language's words moves one setting: active is push and passive pull; volatile and untracked set the threshold; the prefixes set the affect and the cursor. With Signal directly they are options, named after the setting (new Signal()).

The clock. One outermost write, together with everything that runs because of it, is a wave; a batch is one wave. Every node records the wave it was created in and the wave it last ran in. Each wave advances the clock by the engine's speed (1 by default, so ticks and waves count the same). No decision in the engine depends on the speed, so the same program produces the same log in the same order at any speed.

Autonomous Parameterized Memoization

A passive method that takes arguments keeps one answer per set of arguments. The first call with a given set computes; the next call with the same set reads the kept answer. Each answer tracks what its computation read, so it is computed again only when one of those changes — and only when somebody asks for it.

  rate = 2;
  passive area(w, h) {
    console.log('computing', w, h);
    return w * h * this.rate;
  }
}

"Autonomous" because you manage nothing: no cache keys, no invalidation. "Parameterized" because the cache is keyed on the arguments you pass. An answer is a node, so an effect that reads sheet.area(2, 3) runs again when that answer changes, and not when another one does.

What it keeps. An object argument is matched by identity and held weakly: when the object is garbage-collected, the answers made for it go too. The answers belong to the element: they sleep with it, and go when it is disposed or collected. A memo keeps at most 10,000 answers, dropping the oldest first. One caveat: an answer that contains its own argument (return { item }) keeps that argument alive until the element goes.
Union and consensus, at depth. A ΔΔ field tells its readers when any key at any depth is written; a ΣΣ field waits until every key has been written — the same union/consensus difference as $ and $$, applied inside the value. A reader of one key of a Δ or Σ field is told on each write of that key.

Classes

Every DOM event type is a global class: Click, MouseDown, KeyUp, FocusIn, Wheel, PopState… Each one creates a real browser event and delivers it through the browser's own listeners. Underneath, an event is a signal that carries no value and keeps nothing — the same engine as a field, used for things that happen rather than things that are. 0.87.z

The vocabulary & naming

Each class is named after its event type in PascalCase, with the word boundaries put back: dblclick → DblClick, contextmenu → ContextMenu, popstate → PopState, beforeunload → BeforeUnload, visibilitychange → VisibilityChange. Families keep their prefix — MouseDown, PointerCancel, TouchStart, AnimationIteration — and a bare family name exists only where the browser has such an event: Focus and Drag are events, so they are classes; Key, Mouse and Pointer are not, so there is no class for them.

When a name is taken. If the name already belongs to an element class or to any global, the event class gets an Event suffix: input → InputEvent, select → SelectEvent, reset → ResetEvent, storage → StorageEvent (the browser's own Storage has the plain name). Every event class is always available as Instance.Events.Name, whatever happened to the global.

Delivery semantics — what your handlers can rely on

Description: Each handler is a listener of its own on the target, run in the order the handlers were added, and every delivery is also a pulse in the engine (below). The event is the browser's event, dispatched the browser's way, so:

Events × signals — the two delivery planes

Description: Every event delivery is also a node in the engine, so an effect or a formula can depend on an event like on any signal. The everyday pattern needs none of that, though: the handler writes a field, and the effects that read the field react.

  new Click({ target: c }); new Click({ target: c });
  c.textContent;                                      // "n=2" — every occurrence counted

Handlers themselves run outside the engine's tracking: a handler that reads state does not make the event depend on that state. (If it did, a handler under a consensus barrier would skip every click until all its inputs had changed.) Handlers run on every event, whatever they read; an effect that wants the event as a signal still gets it.

Known issue (measured at 0.92.0). A link, navigate() and the back button each fill the default outlet, but at load it stays empty until the first navigation, and a named outlet stayed empty throughout. Both are being looked at.

FAQ · How it works

Why a classic script and not a module?

Because the script tag is the configuration: Instance reads the attributes on document.currentScriptⓘ (Tooling), and a module has no currentScript. It also keeps the model simple: one file runs, and the classes exist. Module code can still reach Instance through InstanceReady and the IVC broker.

Can it coexist with React / another framework on the page?

In default mode, yes: Instance elements are ordinary elements, other code sees nothing unusual, and Instance takes a global name only where it is free. Engine mode is the exception, because it takes over the page. The jQuery merge exists because living beside other code is meant to work.

Server-side rendering?

Not at this version. Instance boots against a live document; it runs in jsdom for tests, but there is no hydration.

TypeScript?

No editor types ship at this version. The surface is shaped like the platform's — an element is its DOM type — so typings would be tractable, and .its (Instance TypeScript) is on the roadmap. The types the runtime enforces are the Superset's: an interface names a field's type, and a write of another type throws.

What does ⚡ do?

It turns on engine mode, which says the whole page is yours. An element the browser makes already has its tag's class behind it, whether it came from document.createElement, from innerHTML or from the page's own markup: it is an Instance element straight from the parser. With ⚡ its constructor is that class too, a parent reaches its children by their tag, and an element has Array's methods. ⚡ on the script tag is Instance.powerup() when the page loads.

A class's own tag — static id

Description: A class that extends a tag class makes that tag: class BigCard extends Div makes <div>s, each carrying data-is="bigcard" so that CSS can tell them apart (BigCard.selector is div[data-is~="bigcard"]). A class that extends Instance itself makes a tag of its own, named after the class in lowercase: class Scrollbar extends Instance makes <scrollbar>. When the tag should not be the class's name — a tag with a dash, say — the class says so with static id: class TabStrip extends Instance { static id = 'tab-strip'; } makes <tab-strip>.

Why id. JavaScript fixes a class's name: it is the identifier you declared, read-only, and it cannot hold a dash. The DOM's word for "what this one is called" is id, so a class's id is its tag, and it is the one name Instance uses for the class everywhere: the tag of the elements it makes, String(TabStrip) ('tab-strip'), TabStrip.selector, the data-is of a subclass of a tag. Without static id the class's name stands in, lowercased. Measured in jsdom, 20 Nov 2026 (probes/static-id.js).

The one rule for names. A class is never named like an element class, in any casing: class Title extends Div and class DIV extends Instance are both refused (InstanceError: class Title is named like the element class of <title>…), because the name would say one tag and the element be another. Tag names are read as the browser reads them — lowercased, in Unicode normal form — and static id is read the same way.
